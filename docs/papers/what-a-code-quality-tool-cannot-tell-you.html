What a code quality tool cannot tell you

Ten numbered defects in one measuring instrument, six of them found in a single day by people who did not build it, and the six questions no static code quality tool can answer about your codebase.

Author

SummaryThe argument in one page

A code quality tool that reports a clean bill of health for code it could not read is lying. That sentence has been in this instrument's source for a year, as a comment, next to the check that enforces it. It was enforced for one of the six ways a tool can fail to read your code, and not for the other five.

This paper is the record of finding that out. The subject is a measuring instrument I built and published: an auditor that scores code on security density, cyclomatic complexity, duplication, specification fidelity and rework. Ten defects in it are written up as numbered, dated records in its public repository. Three published figures have formal errata. Six of the ten were found on 23 November 2026, at the Lagos AI Summit, by three builders who ran the tool on their own machines and their own code, owed me nothing, and reported what broke.

The defects are not ten separate mistakes. They fall into four classes, and each class is a general property of how static analysis is built rather than a quirk of this implementation:

  1. Answering a question that does not apply, instead of declining to answer.
  2. Arithmetic that cannot fail: a rate divided by a large codebase, with severity discarded on the way.
  3. No model of who wrote the code, so a team is charged for libraries they vendored and build output they never typed.
  4. No model of the tool's own environment, so a missing dependency becomes either a crash or, far worse, a silent zero.

From those four classes come six things no tool of this kind can tell you, each demonstrated on itself with the figures and the file. The paper ends with a protocol: six tests you can run against any code quality tool you currently trust, including mine, in under an hour.

I can write this paper because the defect records were published before anyone asked for them. An instrument with no public failure record cannot produce this document, because it has nothing to cite.

1How the figures in this paper are graded

The instrument grades every number it reports before reporting it. The same discipline applies to this paper, and the grades are stated so a hostile reader can go straight to the weakest claim.

Evidence grading used throughout. The practice rule is that a partly measured result is never a result passed: any withheld element makes the aggregate incomplete, never a pass.
GradeMeansWhere it applies here
Measured Reproduced in this repository, pinned by a test that fails on the prior version Every mechanism described: the banding, the provenance rules, the invocation fix, the 0.6.10 before and after
Reported From a run on a user's machine, which I have in full but did not re-run myself All figures from the production CRM: the line count, the 719 findings, the duplication percentage
Withheld Cannot be established from what I have Whether any other tool has these defects. Stated as a hypothesis with a test, never as a result

What this evidence base is, exactly

One instrument, audited by its own author, plus three external users at one event on one day. That is a descriptive account of a single case. It is not a sample, nothing here is inferential, and no claim in this paper is tested for significance, because there is nothing to test it against.

Its value is not statistical. It is that the mechanisms are visible: for each defect you can read the line that caused it, the figure it produced, and the test that now prevents it. A single case with a published mechanism travels further than a survey with a hidden one, and it is the only honest thing a sample of one can offer.

3Four classes, and why they are not specific to me

Class 1. Answering a question that does not apply

Four records have one shape. The instrument was asked a question whose precondition was absent, and it produced a number instead of declining. Fidelity against no brief. Governance against a subject that is not an agent. Drift measured over code whose structure had never been read.

Grading the evidence does not fix this, because a perfectly graded reading of the wrong subject is still wrong. The repair is a gate built before the metric, and the honest output when the gate closes is not a lower score. It is no score, plus the sentence naming what is missing and how to supply it.

This generalises because the incentive is universal. A tool that returns a number on every input looks more useful in a demonstration than one that sometimes refuses, and the refusal is the harder thing to build.

Class 2. Arithmetic that cannot fail

The security metric was a rate: findings per thousand lines, banding at 50 and 100. Fifty per thousand is one security finding every twenty lines. No real codebase reaches that, so the band was green on every project the tool was ever pointed at. On a codebase of roughly 304,000 lines it would have needed 15,193 findings to say "warn" and 30,386 to say "critical". It had 719, nine of them high severity for dynamic code execution from a string, and it printed:

Security   2.40   OK   719 findings

Two compounding errors. A density divides by size, so a large codebase is rewarded for being large: the same nine findings in a 3,000-line service would have measured 240 per thousand lines and banded critical, with identically dangerous code and only the denominator changed. And division discards severity entirely: one high-severity call to eval and one low-severity style note count the same toward the rate, and the rate was all the band ever saw.

Erratum 001 is the same class from the other direction. The scanner counted every assert statement, including assertions inside test files, where the assertion is the test. Roughly 77% of one published figure and 86% of another were test assertions. The metric was, in effect, penalising the subjects that tested their own work.

Class 3. No model of who wrote the code

Of the nine high-severity findings in that report, eight were in vendored libraries and the ninth was upstream framework code. Not one was written by the team being audited. The report's first recommendation was to validate the nine high flags first, which sends an engineer to audit jQuery.

A guard for this existed and missed, which is the instructive part. It matched directory names: vendor, third_party, node_modules. Codebases of that age vendor into ordinary paths such as include/javascript/jquery/ and modules/AOR_Charts/lib/pChart/, where nothing is called vendor. The guard was built and it misses the commonest layout there is.

The same blindness produced citations a reader can do nothing with, pointing at line 1 of a minified file that has exactly one line. Minification also trips the heuristics by construction: packers rewrite code into string concatenation and dense property assignment, which are the shapes a source scanner looks for. Those findings are properties of the packer, not of the authored code.

Class 4. No model of the tool's own environment

The scanner was invoked as a bare command name, resolved through PATH. Installing into a virtual environment and running it without activating that environment is normal, is what every continuous integration job does, and was the exact sequence in the reporter's steps. The scan died with a traceback. The dependency was installed, correctly, precisely where it belonged, and could not be found.

Six acceptance runs from "clean" virtual environments had been written in this repository to prove earlier releases installed correctly. Every one of them passed. The environments were clean; the machine was not, because the scanner also sat on the developer's own PATH, so the bare command resolved every time. A clean environment inside a dirty one does not test what it looks like it tests. Reproducing the crash required stripping the environment entirely.

The crash was the visible half. The dangerous half is what a more forgiving implementation would have done: skip the language it could not scan and report a density of 0.00, which bands green. That is the failure this instrument exists to detect in other tools, and it was one exception handler away from committing it.

4Six things a code quality tool cannot tell you

Each of these is demonstrated above on this instrument, with the record to check. Each is a limit of the method, not of the effort: more rules and better heuristics do not remove any of them.

Cannot tell you · oneWhether the code it could not read is safe

Coverage and verdict are different quantities, and almost every tool reports the verdict in the prominent position. A file that failed to parse, a language with no analyser installed, a dependency that could not be run: each produces zero findings, and zero findings banded against a threshold reads as a pass.

Ask what share of your lines were actually read. If the tool cannot tell you, every number it gives you is conditional on an unknown denominator.

Cannot tell you · twoWhether the number has been diluted by size

Any per-thousand-lines figure improves when you add code. A team that ships a large framework alongside a small amount of dangerous work will measure better than a team that ships only the dangerous work. The metric rewards the denominator.

Ask for the count as well as the rate, and the worst severity present as well as both. If a dashboard shows you only the rate, it is showing you the quantity most easily improved without changing anything.

Cannot tell you · threeWhether a finding is exploitable

This instrument produced a textbook demonstration against itself. An external reader reported that a call accepted any URL scheme and could therefore read local files. That was a false positive: a check nine lines above already refused every scheme but https.

The reported line was right, for a reason nobody had looked for. The call followed redirects, and the standard redirect handler permits the new location to be plain http, so a server answering with a redirect would have moved the payload onto a cleartext connection. The promise held once, on the first URL, and did not survive the first redirect.

So a careful reader took a static finding at face value and reported correct code as broken, and the same report found a real defect no test was looking for. Both halves are the same lesson: a static finding is a place to look, never a verdict. A tool that presents it as a verdict is making a claim it has no way to support.

Cannot tell you · fourWhose code it is reading

Without a provenance model, every file in the tree is charged to whoever is standing in front of the report. Vendored libraries, generated clients, build output, migrations, upstream framework code: all of it becomes your team's quality score, your team's security debt, and your team's remediation list.

The repair is attribution, not exclusion. A number that quietly stops counting things is the same class of error as one that quietly counts them, so files that are not first-party are named and set aside in the open, with the count shown.

One warning for anyone building this: every rule needs a positive signal, because misclassifying a team's own file as third-party hides a real finding, which is the costlier direction to be wrong in. A directory called lib is not a signal. Plenty of teams keep their own code there.

Cannot tell you · fiveWhether the code does what you asked for

No tool built on linting can see missing work, because none of them knows what was requested. This is the failure mode that matters most in practice: four of five features built, success reported, and nothing in the output that could notice.

A tool can only answer this against a specification a human supplied. When this instrument inferred a brief from commit subjects instead, it harvested a list of errands and reported zero of twelve delivered, which impugns the guess rather than the code. A derived brief is never a measurement, however much of it happens to match, because the thing in doubt is the brief.

Cannot tell you · sixWhether its own installation is intact

A tool is a process on a machine, with dependencies that resolve or do not, on an operating system that may not be the one it was written on. Every one of the installation failures reported from the field was a command line failure: a resolution step that worked on the author's machine and nowhere else.

Most tools treat this as the user's problem and report nothing. The honest design is a self-check that names what works, what does not, what each gap costs in lost coverage, and the exact command that fixes it. Mine did not have one until the day users needed it.

5The protocol: six tests to run on any tool you trust

Here the paper stops describing one instrument and becomes usable. Each test below detects one of the six limits, on any tool, in minutes. Each was derived from a defect in my own and is pinned by a test in my own repository.

What this protocol can and cannot establish is worth stating plainly. It establishes behaviour on your tool, on your machine, today. It does not establish anything about a vendor's quality in general, and a failure on one test is a finding to raise, not a verdict to publish.

Six tests, derived from findings 002 and 005 to 010. A tool that passes all six is not correct; it is honest about six specific ways of being wrong.
TestDo thisA failing toolAn honest tool
1 Remove one language's analyser, or feed it a file that cannot parse, then scan Reports zero findings for that language and bands it as a pass Drops coverage, names the language as unread, and says why
2 Scan a small project with one serious finding. Then concatenate a large library into it and scan again The grade improves The grade does not move, because the worst finding present decides it
3 Take its most severe finding and try to exploit it, or read the twenty lines around it Presents it as a confirmed vulnerability with a severity and no caveat Presents it as a location to review, with the rule that fired and the evidence
4 Vendor a library into an ordinary path, not into a folder called vendor, and scan Charges the library's findings to your team and tells you to fix them first Names the file as third-party, sets it aside, and shows the count it set aside
5 Ask it which of the things you asked for were not built Answers from the code alone, or infers a specification and measures against it Declines until a specification is supplied, and says how to supply one
6 Install it into a fresh environment, do not activate that environment, and run it on a machine with a stripped PATH and on Windows Crashes, or silently skips what it cannot run Runs, or tells you exactly what is missing and what to type

One note on test six, because it is the one that fooled me

A virtual environment created inside your normal shell is not a clean environment. The tool you think you removed may still be on your own PATH, and the bare command will resolve every time. The test only means anything with the environment stripped:

env -i HOME="$HOME" PATH="/usr/bin:/bin" ./env/bin/your-tool scan .

Six acceptance runs in my own repository missed a crash that a user hit within minutes of installing, for exactly this reason.

6What the instrument now does instead

Six design rules, each the repair for a numbered defect, each pinned by a test that fails on the previous version. They are stated as rules rather than as patches because the patch is not the contribution.

The gate comes before the metric

Does the question apply to this subject at all? Fidelity requires a supplied specification. Governance requires a subject that both calls a model and has a path to act. When the gate closes, no score is produced and the output names what is missing.

Every reading carries what it rests on

Three grades, with no threshold to tune: measured, provisional, withheld. A derived input is never promoted to a measurement by matching well. A partly measured standard is incomplete, never passed.

The worst finding decides the colour

A density may not speak for a severity. One high-severity finding raises the band to critical regardless of how much sound code surrounds it. The asymmetry settles it: a high finding that proves to be a false positive costs a team one review, while a high finding banded comfortable costs them the breach.

Verified end to end on a 12,121-line project carrying a single high-severity finding for dynamic code execution. Its density is 0.08 per thousand lines, which bands as good on its own and cannot soften it:

0.6.5   0.08   OK  →  0.6.10   0.08   RISK

Medium and low findings still do not move the band. One field report carried 694 medium findings, and a rule that always says red says nothing.

Provenance is attributed, never silently dropped

Each file is classified first-party, vendored or generated, from positive signals only: a known library's name as a filename stem or path segment, a build-output filename, and line lengths no author produces. Metrics about the project's code are computed over the project's code, and everything set aside is counted and named in the report.

The tool reports on itself

A single command answers what works, what does not, what each gap costs, and the command that fixes it. It also names every defect still open in the instrument, because an installation report that hides those is the same comfortable green light over an unexamined thing that the rest of this exists to prevent.

Open defects travel with the output

Finding 008 is open as this is published. Duplication on any repository that ships built assets beside their source may be substantially overstated, and that single reading can set the worst band for a whole audit on its own. The fix is known: count a file once per content digest, and say how many copies were collapsed. It is not shipped because it changes the value of a figure already published, which requires an erratum and a deliberate decision rather than a quiet edit.

Meanwhile it is disclosed in every receipt the tool issues, and a test asserts that the disclosure is still there. When it is fixed, that test fails. That is the point of it.

7The case that matters next: tools read by agents

Everything above assumed a person reads the output. That assumption is expiring, and it was carrying more weight than anyone noticed.

Consider the reading that started this. A green dot, the word OK, a density of 2.40, and 719 findings on the same line. A human looked at that, became suspicious, and filed a report. The suspicion came from the incongruity: a reassuring colour sitting next to a large number.

A language model given the same line does not become suspicious. It summarises. "The security scan passed with a density of 2.40" is a faithful summary of a dishonest reading, and it will be passed upward with the incongruity smoothed away, because smoothing is what summarising is. Every weakness in this paper gets worse when the reader is a model, because the one safeguard that caught it was a human finding the output strange.

Two consequences for anyone exposing analysis to an agent.

Limits must be structured fields, not prose

A caveat in a sentence is something a model may or may not carry forward. A caveat as a named field in a structured result is something it must step over: what was not measured, what the coverage was, which severities are present, which defects in the instrument are open. The honest shape is a result that cannot be read as a pass without also reading what it could not do.

A tool failure is a result, not a protocol error

When the analysis cannot run, the answer to the calling agent must be a result that says so, in the same shape as a successful reading. A traceback thrown into a model's context is the worst of all outcomes: it is unreadable, it is unstructured, and the model will confabulate around it rather than stop.

I think this is an unclaimed position, and I want to state its strength accurately. Many servers now expose code analysis to agents. I have not surveyed them, so I claim nothing about what they do. What I claim is narrower and checkable: the question what does this return when it cannot do its job, inside somebody else's agent has a right answer, that answer is not a traceback, and it is the same doctrine this paper applies to a human reader, pointed at a machine one.

8What this paper does not establish

  • Nothing about any other tool. The four classes are properties of how static analysis is built, and I believe they are widespread, but belief is not a result. Section 5 exists so that anyone can convert it into a result on their own tool rather than taking my word for it.
  • Nothing statistical. One instrument, one event, three users, one day. Descriptive throughout. No significance is claimed or tested.
  • No completeness. Ten defects found is not ten defects existing. The honest reading of this record is that an instrument with a hard look taken at it yields about ten, and that the next hard look will yield more. Finding 008 is open; the thresholds behind the density bands are still almost certainly wrong by an order of magnitude, and nothing in the repository records where they came from.
  • No claim of adoption. Three external users on one day are three external users on one day. Install counts, registry listings and sign-ups are distribution signals, not adoption and not revenue. A count is not an economy, and that rule applies to my figures first.
  • No safety claim of any kind. Use a tool of this sort as a second reader, never as a judge whose word is final. Anyone claiming their tool makes software safe is selling you something.

The most valuable work on this instrument that day was done for free by people who did not build it. The lesson is not to test harder in private. It is to get the thing in front of strangers sooner, because strangers have dirty machines and ugly codebases, and that is the only place these defects live.

Reproduction

Every record cited here is a file in the instrument's public repository under docs/, named for its number. Each describes the defect, the mechanism, the figure it produced, the repair, and the test that pins it. Fixes are tagged by version: 0.6.1, 0.6.4, 0.6.7, 0.6.8, 0.6.10. The suite at 0.6.10 is 546 tests.

Figures attributed to a production codebase are from a user's own run, supplied in full, and are labelled Reported for that reason. The mechanisms behind them are reproduced on synthetic fixtures in the test suite, which is what Measured means in section 1. No real customer data is held, used or published.
